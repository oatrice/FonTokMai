# 📊 Tradeoffs Analysis: Radar Image Storage (Rolling 3 Hours)

**บริบทของข้อมูล (Context)**
- เราต้องโหลดภาพเรดาร์ (GIF) ทุกๆ 15 นาที
- ขนาดไฟล์ประมาณ 1-3MB ต่อสถานี 
- มี 3 สถานีหลัก = 12 อัปเดต/ชั่วโมง (รวม ~30MB/ชั่วโมง)
- เก็บย้อนหลัง 3 ชั่วโมง = มีข้อมูลหมุนเวียนในระบบตลอดเวลาที่ **~90-100 MB**

ที่ผ่านมา SQLite ไม่เหมาะเพราะการเขียน/ลบ BLOB ขนาดใหญ่บ่อยๆ ทำให้ไฟล์ DB เกิด Fragmentation และบวม (Bloat) นำไปสู่ปัญหา Scale ครับ นี่คือการเปรียบเทียบ Cloud Storage/DB ตัวอื่นๆ ครับ

---

## 1. Cloud Firestore (NoSQL)
**❌ ไม่สามารถใช้ได้ (Unusable for this case)**
- **ข้อจำกัด (Hard Limit):** Firestore จำกัดขนาด Document ไว้ที่ **1MB ต่อ Document** เท่านั้น ไฟล์ GIF ของเราขนาด 2.5MB จึงบันทึกลงไปตรงๆ ไม่ได้เลย (เว้นแต่จะหั่น Chunk ซึ่งผิดวัตถุประสงค์และเปลืองโควต้ามาก)
- **ค่าใช้จ่าย:** Firestore คิดเงินตามจำนวน Read/Write การบันทึกและลบ Chunk ข้อมูลทุกๆ 15 นาทีจะทำให้ Cost บานปลายโดยไม่จำเป็น

## 2. Cloud SQL (PostgreSQL)
**⚠️ ทำได้แต่ไม่แนะนำ (Anti-pattern)**
- **ข้อดี:** รองรับข้อมูลแบบ BLOB ได้สบาย (สูงสุดระดับ GB)
- **ข้อเสีย:** การเก็บไฟล์ภาพ (Binary) ลงใน Relational DB เป็น Anti-pattern ที่ทำให้ Database บวมโดยใช่เหตุ ส่งผลให้การทำ Backup/Restore ช้าลงมาก และเปลือง Memory ของ DB Engine
- **ค่าใช้จ่าย:** พื้นที่จัดเก็บแบบ SSD บน Cloud SQL มีราคาแพงกว่า Object Storage ทั่วไปหลายเท่า

## 3. Redis (In-memory Cache)
**⚡️ เร็วที่สุด แต่แพงถ้าข้อมูลใหญ่**
- **ข้อดี:** 
  - ความเร็วระดับ Millisecond เหมาะกับการอ่าน/เขียนบ่อยๆ 
  - มีระบบ **TTL (Time to live)** สามารถตั้งให้ลบไฟล์อายุเกิน 3 ชม. ได้อัตโนมัติ (ไม่ต้องเขียนโค้ด Cleanup)
- **ข้อเสีย/ค่าใช้จ่าย:** ข้อมูลจะถูกเก็บไว้ใน RAM ซึ่งมีราคาแพงมาก การเก็บภาพเรดาร์ 100MB หมายความว่าคุณต้องเสีย RAM ของระบบ/Cloud Redis ไป 100MB ฟรีๆ ถ้าอนาคตเพิ่มเป็น 20 สถานี RAM อาจจะพุ่งไปแตะ 1GB ได้
- **สรุป:** เหมาะถ้าระบบต้องเอาภาพมาใช้ประมวลผลทันทีในหน่วย Millisecond และยอมจ่ายค่า RAM ได้

## 4. GCS (Google Cloud Storage) / Firebase Storage
**🏆 ทางเลือกที่ดีที่สุด (Industry Standard)**
- **ข้อดี:** 
  - ถูกสร้างมาเพื่อเก็บไฟล์ Binary (รูปภาพ, วิดีโอ) โดยเฉพาะ
  - Scale ได้ไม่จำกัด ฐานข้อมูลหลัก (DB) จะไม่บวมเพราะเก็บแค่ URL หรือ Path ของไฟล์ 
  - มีฟีเจอร์ **Object Lifecycle Management** สามารถตั้ง Rule ให้ลบไฟล์เก่ากว่า X วัน/ชั่วโมง ได้อัตโนมัติโดยฝั่ง Cloud
  - ปัจจุบันโปรเจกต์คุณมีการใช้ `firebase_admin` อยู่แล้วใน `firestore.py` จึงสามารถเชื่อมต่อเข้ากับ Firebase Storage Bucket (GCS) ได้ทันที
- **ค่าใช้จ่าย:** ถูกที่สุด (คิดเป็น Cents ต่อ GB)

---

### 💡 คำแนะนำ (Recommendation)
สำหรับ Use case "เก็บภาพเรดาร์เพื่อนำมาดึงเฟรม/แสดงผล แบบหมุนเวียน"
ผมแนะนำให้ใช้ **GCS (Firebase Storage)** ครับ เพราะ:
1. ตรงตาม Best Practice ที่สุด
2. นำไปประยุกต์ทำ Public URL ให้แอปฝั่ง Client โหลดไปแสดงเป็น Animation ได้โดยตรง (ลดภาระ Backend)
3. ไม่กินโควต้า Database 

แต่หากเป้าหมายของคุณคือ นำภาพมาคำนวณ Optical Flow ทุกๆ เฟรมอย่างต่อเนื่อง และต้องการความเร็วสูงสุด (ไม่แคร์ราคา RAM) **Redis** จะเป็นตัวเลือกที่สูสีครับ

คุณอยากให้ผมเปลี่ยนจาก SQLite ไปเชื่อมต่อกับ **GCS (Firebase Storage)** หรือ **Redis** ดีครับ?
